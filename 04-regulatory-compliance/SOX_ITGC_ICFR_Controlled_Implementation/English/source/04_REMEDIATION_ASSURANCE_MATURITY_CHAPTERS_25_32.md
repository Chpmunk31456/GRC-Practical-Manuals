# Manual 13 — SOX ITGC / ICFR Controlled Implementation

## Chapter 25 — Remediation planning
For each finding, identify root cause, affected control objective, impacted systems/processes, risk owner, corrective action, target date, interim control, evidence required, and retest criteria. Avoid closing findings merely because a technical change was deployed; verify that the redesigned control is operating and that related dependencies were addressed.

## Chapter 26 — Retesting and closure
Retesting should confirm both remediation design and operation. Define a sufficient post-remediation observation period based on control frequency and risk. Retain the original finding, remediation evidence, retest evidence, reviewer conclusion, and closure approval. Reopen the issue if remediation introduces a new control gap or if operating evidence is insufficient.

## Chapter 27 — Management certification support
Build a certification-support process that aggregates control status, significant changes, deficiencies, remediation status, disclosure-process inputs, and unresolved issues. Technology representations should be evidence-based and traceable to control owners and period-specific evidence. Escalation should occur before certification deadlines, not after evidence has been finalized.

## Chapter 28 — External-auditor interaction
Maintain a controlled evidence handoff process with request tracking, ownership, due dates, version control, and issue escalation. Respond to auditor requests accurately without changing underlying evidence merely to fit the request. Track auditor observations separately from management’s own deficiency evaluation until the responsible decision makers reconcile them.

## Chapter 29 — Continuous monitoring and reassessment
Use dashboards, exception analytics, access recertification, change metrics, incident data, failed-job trends, control attestations, and remediation aging to identify deteriorating control performance. Monitoring does not replace control operation or independent testing. Define thresholds that trigger deeper review, scope reassessment, or control redesign.

## Chapter 30 — Essential, Structured, and Enhanced implementation paths
Essential organizations establish a defensible scope, core ITGC inventory, ownership, evidence, and deficiency process. Structured organizations add formal risk/assertion linkage, population controls, standardized testing, service-provider governance, and integrated remediation. Enhanced organizations add continuous monitoring, automated evidence provenance, configuration analytics, cross-system lineage, and change-triggered reassessment. Maturity does not change legal obligations; it changes the reliability and efficiency of control execution.

## Chapter 31 — Common failure modes and practitioner scenarios
Common failures include over-scoping generic cybersecurity controls, relying on screenshots without population evidence, treating SOC reports as automatic assurance, weak IPE validation, unresolved privileged access, emergency changes without retrospective review, spreadsheet drift, incomplete interface monitoring, and remediation closure without retesting. Use scenario exercises to test whether practitioners can identify the ICFR risk, required evidence, escalation route, and affected dependencies.

## Chapter 32 — Final release and operating checklist
Before using this manual as an operational baseline, verify current SOX/SEC/PCAOB source status, scope, ownership, control-to-risk traceability, evidence design, localization fidelity, accessibility, provenance, and change history. For repository publication, require the exact candidate hash, trilingual source hashes, DOCX/PDF hashes, QA results, source verification record, review evidence, checksums, manifest, workflow security, predecessor publication, catalog/release-registry reconciliation, and standing release authorization. Any material change after review reopens only affected gates.
